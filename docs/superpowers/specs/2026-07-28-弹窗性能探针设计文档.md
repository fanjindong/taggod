# 弹窗性能探针设计文档

## 结论

本次不再预设优化点，先在弹窗内长期保留一个本地“飞行记录器”。它记录每次弹窗从 Navigation Timing `0` 到真实数据已渲染、控件已恢复且浏览器至少获得一次绘制机会的关键时间点，并在该边界之后把最近 `20` 个样本写入 `chrome.storage.local`。用户再次遇到慢弹窗时，可从弹窗底部直接打开“性能诊断”并复制记录，不必临时改代码、重现问题或打开 DevTools。

探针只使用浏览器原生 API，不新增权限、依赖、构建步骤、后台消息或远端上报。启动期间只做 `performance.now()`、对象赋值和 Performance Observer 采集；数值舍入、历史读取、JSON 序列化和写入均推迟到可用绘制边界之后。

这是一项取证能力，不把尚未验证的相关性写成优化结论，也不承诺它本身缩短弹窗耗时。

## 已确认事实

同一版代码已取得一个慢样本：

- `responseEnd = 2898.8ms`。
- `scriptStart = 4504.1ms`，即响应完成至 `popup.js` 开始执行之间约 `1605.3ms`。
- `currentTabs`、`allTabs` 和 storage 同时开始，约在 `815ms` 后一同结束，彼此结束时间差不足 `1ms`。
- 状态构建 `6.3ms`，初次 `render()` 为 `135.8ms`。
- 控件恢复于 `5519.4ms`，FCP 为 `6280ms`。

后续同版快样本中，`scriptStart` 为 `87.1ms`，FCP 为 `508ms`；资源预取实验的 `scriptStart` 为 `89.7ms`，FCP 为 `248ms`。这说明后两次“感觉很快”主要来自 Chrome、操作系统和标签恢复状态不同，不能归功于资源预取。取消自动重复概览也未表现出稳定的 FCP 阻塞关系。FCP 只是整个文档第一次出现内容，静态标题或搜索框可能先于真实标签结果绘制，因此它不能单独代表弹窗可用。

因此，拆分 `allTabs`、资源预取或取消重复概览都没有足够证据作为首开优化主方案。常态化探针应先回答耗时落在哪个区间，再决定是否修改业务路径。

## 目标

- 每次打开弹窗都自动记录同一口径的启动样本，保留最近 `20` 次。
- 区分文档响应、`grouping.js` 前等待、`grouping.js` 执行、`popup.js` 前等待、Chrome API、状态构建、DOM 渲染和可用绘制等待。
- 记录本扩展会话内“已达到冻结边界”的弹窗样本序号，方便比较首个可记录样本与后续样本。
- 用户不依赖 DevTools，点击一次便可复制可粘贴分析的 JSON。
- 探针故障、存储故障和复制故障均不得改变弹窗业务结果。
- 不记录网址、标题、标签编号、搜索词、规则内容、工作集内容或 storage 值。

## 非目标

- 不自动诊断根因；区间相关性只能用于缩小范围，因果关系仍须对照实验确认。
- 不自动上传、联网、告警、画趋势图或接入服务端监控。
- 不缓存标签状态，不常驻或主动唤醒 service worker。
- 不新增配置开关、采样率、用户可调阈值或通用埋点框架。
- 不把“本扩展会话首个可记录样本”命名为实际第一次打开或严格冷开。
- 不在本次设计中实施任何未经验证的性能优化。

## 测量边界

所有毫秒值均来自同一弹窗文档的 `performance.now()` 或 Performance Entry `startTime`，以 Navigation Timing `0` 为起点，保留一位小数。

探针能覆盖：

1. 弹窗文档导航开始后的响应、首个共享脚本、弹窗业务脚本、Chrome API、状态构建、DOM 更新、FCP 和可用绘制边界。
2. `popup.js` 开始执行后的 Long Task。
3. 首次 `loadState()` 及首轮自动重复概览在可用绘制边界时的状态。

探针不能覆盖：

1. 用户点击扩展图标到弹窗文档 Navigation Timing `0` 之间的等待。配置了 `default_popup` 时，`chrome.action.onClicked` 不会提供可靠起点。
2. `popup.js` 执行前已经结束的 Long Task；此时只能用 `groupingScriptStart`、`groupingScriptEnd` 和 `scriptStart` 缩小区间，不能取得任务归因。
3. 首次 `loadState()` 永久不结束、或弹窗在可用绘制边界前被用户关闭的样本。页面销毁后无法保证异步 storage 写入完成。

若用户主观等待很久，但记录中的 Navigation Timing、`navigationToUsable` 和 FCP 都很快，则须用 Chrome Performance 轨迹补测“点击到 Navigation Timing `0`”，不可据此声称用户感知有误。

## 采集点

### Navigation Timing

在 `window.load` 后的下一宏任务、样本冻结前读取一条 `PerformanceNavigationTiming`：

- `responseEnd`
- `domContentLoadedEventStart`
- `domContentLoadedEventEnd`
- `domComplete`
- `loadEventEnd`

`window.load` 处理器执行期间 `loadEventEnd` 仍可能为 `0`，因此处理器只记录业务时间点，并在下一宏任务读取 Navigation Timing。该宏任务中 `loadEventEnd > 0` 才保存数值；仍为 `0` 或导航条目缺失时保存 `null`，并将 measurement 标为 `partial`。

### 业务时间点

- `groupingScriptStart`：`grouping.js` 第一条可执行语句，仅在 `document` 和 `performance.now` 均可安全使用的弹窗上下文记录。
- `groupingScriptEnd`：`grouping.js` 完成命名空间导出之后。
- `scriptStart`：`popup.js` 第一条可执行语句用局部 `try/catch` 安全捕获当前时间，随后才读取并删除两个临时 grouping 时间点。
- `domContentLoadedHandlerStart`：现有 `DOMContentLoaded` 回调入口。
- `windowLoad`：`window.load` 回调入口；它不直接触发冻结，冻结检查由下一宏任务执行。
- `loadStateStart`：首次 `loadState()` 入口。
- `stateReady`：浏览器状态读取和快照构建完成。
- `controlsReady`：首次 `loadState()` 的 `finally` 中恢复控件之后。
- `usableReadyToPaint`：首次状态加载结束、初次 `render()` 已完成且 `setBusy(false)` 已执行后，第一个 `requestAnimationFrame` 回调入口。
- `usablePaintOpportunity`：在上述回调内再注册一次 `requestAnimationFrame`，记录第二个回调入口；它表示浏览器在两次回调之间至少获得过一次绘制机会，不伪称为像素已上屏时间。
- `firstPaint`：Paint Timing 的 `first-paint`。
- `firstContentfulPaint`：Paint Timing 的 `first-contentful-paint`，简称 FCP。

只测弹窗生命周期内第一次 `loadState()`；整理、去重或保存操作触发的后续刷新不覆盖启动样本。

### 阶段与浏览器调用

每项记录 `start`、`end`、`duration`、`outcome` 和可用时的 `count`：

- `commands`：`chrome.commands.getAll()`。
- `currentTabs`：`chrome.tabs.query({ currentWindow: true })`。
- `allTabs`：`chrome.tabs.query({})`。
- `storage`：启动所需的 `chrome.storage.local.get()`。
- `browserStateRead`：三项启动状态读取的整体等待。
- `stateBuild`：归一化设置、构建标签快照和概览。
- `render`：初次 `render()` 同步执行。
- `loadState`：首次 `loadState()` 整体执行。
- `duplicateOverview`：首轮自动重复概览请求；不等待它完成才冻结样本，是否跨过可用边界或 FCP 分别由其 `start`、`end` 与对应时间点比较。

`outcome` 只取 `success`、`error`、`pending`、`not-started` 或 `unsupported`。不保存异常原文，避免错误消息意外携带用户数据。

### Long Task

若浏览器支持 `longtask` Performance Observer，则从 `scriptStart` 起累计：

- 总数量。
- 总时长。
- 最大时长。
- 最多 `20` 条 `{ start, duration }`；总量统计包含被截断的条目。

不支持时明确记录 `supported: false`，不可把“未支持”解释为“没有 Long Task”。

## 采集与冻结时序

1. `grouping.js` 仅在 `document` 存在时，于 IIFE 外尝试记录 `groupingScriptStart`，并在导出 `TabGodGrouping` 后尝试记录 `groupingScriptEnd`。两处都须同时检查 `performance` 与 `performance.now`，并用局部 `try/catch` 将缺失或异常收敛为 `null`；后台 `importScripts()` 路径不执行探针分支。
2. `popup.js` 第一条语句使用立即执行函数安全捕获 `scriptStart`：先检查 `performance.now`，调用异常时返回 `null`，不得因探针阻止后续业务脚本。随后读取两个临时值、删除临时全局字段并创建单个内存样本；三个起始值任一为 `null` 时，对应派生区间也为 `null`。
3. 立即注册 Paint 和 Long Task Observer；使用 `buffered: true` 获取已经产生的条目。
4. 在现有启动函数边界记录点和阶段。包装函数必须原样返回成功值、同步异常和 Promise 拒绝，不吞掉或改写业务错误；所有数值先保留原始 Number，冻结后才统一舍入。
5. 首次 `loadState()` 的 `catch` 显式记录 startup 失败；`finally` 先执行 `setBusy(false)`，再安排第一个 `requestAnimationFrame`。该回调记录 `usableReadyToPaint`，并安排第二个回调记录 `usablePaintOpportunity`。
6. `window.load` 回调只记录 `windowLoad` 并调用 `setTimeout(tryFreeze, 0)`；下一宏任务设置 `loadEventSettled = true` 并读取 Navigation Timing。不得在 load 回调栈或其微任务中冻结。
7. 若 Paint Timing 已在静态外壳阶段产生 FCP，待 `loadEventSettled` 和 `usablePaintOpportunity` 到达后进入冻结流程；若 FCP 晚于动态渲染，则继续等待实际 FCP。故完整样本的冻结边界和 `navigationToUsable` 都取 FCP 与 `usablePaintOpportunity` 的较晚者，避免指标低估或写盘抢在首次内容绘制之前。
8. Paint Timing 不受支持时，在 `loadEventSettled` 和 `usablePaintOpportunity` 到达后进入 `partial` 冻结流程。首次 `loadState()` 永久不结束、浏览器宣称支持 Paint Timing 却始终没有 FCP，或弹窗提前关闭时不写历史；宁缺样本，也不在未知绘制边界前写盘。
9. 冻结流程先设置一次性 `freezeStarted`，使随后到达的 Observer 回调直接返回；再分别调用 Paint 和 Long Task Observer 的 `takeRecords()`，把尚未投递且 `startTime <= navigationToUsable` 的条目并入现有统计，并立即 `disconnect()` 两个 Observer。随后从内存采集对象生成不可变快照；数值舍入、派生计算和 storage 操作只使用该快照，持久化产生的任务不得再进入本次样本。
10. `duplicateOverview` 在冻结时仍未完成才保存为 `pending`；已经结束时保留真实 `start` 和 `end`，分别与 FCP、`navigationToUsable` 比较，不仅凭先后关系推断因果。

Observer 回调被调度的时刻可能晚于实际绘制，记录必须使用 Paint Entry 的 `startTime`，不能使用回调执行时的 `performance.now()` 代替 FCP。`takeRecords()` 用于补齐已经排队但尚未回调的最后条目，不得省略；`usablePaintOpportunity` 只表示浏览器获得过一次绘制机会，不能改名为“已上屏”。

## 会话标识

样本冻结后才读取 `chrome.storage.session`，保存：

- 随机 `session.id`。
- 递增的 `recordedPopupIndex`。
- `firstRecordedPopup = recordedPopupIndex === 1`。

会话元数据固定使用 `chrome.storage.session` 键 `tabgod.popupPerformanceSession`，随机值由原生 `crypto.randomUUID()` 生成。序号在样本冻结后才分配，只统计已达到冻结边界且成功更新 session 的弹窗；提前关闭、永久等待或 session 更新失败的弹窗不占序号，local 写入失败则可能留下序号缺口。因此 `firstRecordedPopup` 既不证明它是本次 Chrome 会话实际打开的第一个弹窗，也不等于严格冷开。`chrome.storage.session` 还可能因扩展重新加载、更新或禁用后启用而重置；session 读取或写入失败时三个字段均写为 `null`，local 历史仍照常保存。

## 持久化

- `chrome.storage.local` 键名固定为 `tabgod.popupPerformanceHistory`。
- 值固定为 `{ schemaVersion: 1, samples: [...] }`。
- 每次追加后只保留按时间排序的最近 `20` 条，不提供可配置上限。
- 仅在样本冻结后执行一次 local 的读改写；可用绘制边界及所需 FCP 到达前不得读取该键。
- local 读改写由当前页面唯一的 `persistPromise` 表示；开始前和提交前都检查 `suppressCurrentHistory`，使清除操作可以阻止尚未开始或已经读取但尚未提交的当前样本。
- schema 不兼容或值损坏时，只重建性能历史键，不触碰设置、最近访问、工作集或其他用户数据。
- local 读写失败时静默退出，不影响弹窗；当前页面的“性能诊断”面板显示“本次记录保存失败”。不重试、不唤醒后台。

按每条数 KB 估算，`20` 条样本远低于 `chrome.storage.local` 配额。无需压缩、IndexedDB、数据库封装或清理定时器。

## 导出与清除

在 `.quick-action-footer` 中给现有“高级管理”按钮增加一个同级“性能诊断”按钮，并把诊断面板放在 `moreToolsSection` 之外。这样打开诊断不会经过现有 `toggleMoreTools() → loadManagementState() → get-management-state` 路径，也无需改造其他高级管理面板的加载语义。

- 面板固定显示“本机保留最近 20 次弹窗记录”，展开面板本身不读取历史。
- 当前页面只维护一个轻量状态：`collecting`、`persisting`、`saved`、`unavailable` 或 `cleared`。这不是通用状态机，只用于避免当前样本与两个诊断按钮竞态。
- 初始状态为 `collecting`；样本冻结并开始 session/local 操作时改为 `persisting`，local 写入成功后改为 `saved`，探针不可用或写入失败时改为 `unavailable`，清除成功后改为 `cleared`。`cleared` 在当前弹窗生命周期内不可被后续采集覆盖。
- “复制性能诊断”在 `collecting` 时不读取也不复制旧历史，而显示“本次记录仍在采集，请稍后重试”；在 `persisting` 时等待当前 `persistPromise`；在 `saved`、`unavailable` 或 `cleared` 时直接读取历史并复制格式化 JSON。这样不会静默漏掉用户刚遇到的慢样本。
- 导出外层包含 `format: "tabgod-popup-performance"`、`schemaVersion`、`exportedAt`、`sampleCount` 和 `samples`。
- 优先使用用户点击触发的 `navigator.clipboard.writeText()`；失败时在面板展示只读文本并全选，允许用户手动复制，不新增 `clipboardWrite` 权限。
- “清除性能记录”确认时，若已有 `persistPromise`，先让当前样本完成写入，再删除 `tabgod.popupPerformanceHistory`；这样删除失败时当前慢样本仍然保留。若当前仍在采集，则先设置 `suppressCurrentHistory = true` 并建立本次清除结果屏障：后续冻结先更新 session，再等待清除结果；删除成功时不得追加 local 历史，删除失败时恢复写入当前样本。删除成功后状态固定为 `cleared`，当前弹窗不能重新添回样本。
- 复制或清除执行期间临时禁用这两个诊断按钮，完成后只恢复符合当前状态的操作，避免两次用户动作彼此穿插。
- 清除不删除 session 计数，避免把同一扩展会话的下一次弹窗错误标为首次。

打开、复制或清除诊断不得调用 `toggleMoreTools()`、`loadManagementState()`、`loadState()`，不得查询标签或发送后台消息。诊断面板复用现有通用按钮、帮助文本和隐藏样式，不加入 `data-management-panel` 列表。

## 隐私边界

允许保存：

- UTC 时间。
- 扩展版本、Chromium 版本。
- 随机会话值和会话内已记录样本序号。
- 标签数、窗口数。
- 时间点、阶段耗时、Long Task 数值。
- 固定枚举的成功、失败、等待和不支持状态。

禁止保存：

- URL、标题、域名、搜索词。
- `tabId`、`windowId`、groupId、sessionId 等浏览器对象编号。
- 分组规则、工作集、最近访问映射或任何 storage 内容。
- 原始错误消息、堆栈、完整 User Agent。
- 可跨浏览器会话追踪的稳定设备标识。

数据只保存在 `chrome.storage.local`，不会进入 `chrome.storage.sync`。只有用户点击复制后，文本才进入系统剪贴板。

## 证据判读

复制报告后，先按以下区间定位，不跨过证据下结论：

| 现象 | 可确认范围 | 下一步 |
| --- | --- | --- |
| `responseEnd` 已很大 | 耗时发生在文档响应完成前 | 用 Chrome 轨迹检查扩展页创建、磁盘和浏览器调度 |
| `responseToGrouping` 很大 | 响应完成后至首个共享脚本执行前 | 检查 DOM 解析、脚本资源获取和浏览器调度 |
| `groupingEvaluation` 很大 | 共享分组脚本自身执行慢 | 对 `grouping.js` 做 CPU Profile，不把耗时归给 Chrome API |
| `groupingToPopup` 很大 | 共享脚本结束后至弹窗脚本执行前 | 检查脚本调度和两段脚本之间的页面工作 |
| 多个并发 Chrome API 同时变慢、同时结束 | 公共浏览器调度或扩展 API 冷态嫌疑较高 | 做只保留单项调用的受控实验，不任选一个 API 背锅 |
| 只有一个 Chrome API 明显更慢 | 该调用是候选阻塞项 | 移出关键路径做 A/B 验证 |
| `stateBuild` 随标签数上升 | 前端数据构建是候选热点 | 对同一输入做纯函数剖析 |
| `render` 明显上升 | 同步 DOM 构建是候选热点 | 分解 DOM 数量和单次渲染成本 |
| `navigationToUsable` 很大，但读取、构建和渲染都小 | 可用绘制边界前仍有未解释等待 | 对照 `controlsToUsable`、Long Task 和 FCP 检查主线程与绘制调度 |
| FCP 早于 `render.end` | 静态外壳先绘制，FCP 不是动态结果指标 | 以 `navigationToUsable` 为主，不计算 `postRenderFcpDelay` |
| `postRenderFcpDelay` 很大 | 本样本首次内容绘制确实晚于动态 DOM 完成 | 检查主线程、样式布局、合成与浏览器调度 |
| `duplicateOverview` 晚于可用边界才开始或结束 | 它没有阻止本样本到达可用边界 | 不再以该样本宣称取消它可改善可用时间 |

Long Task 为空只能说明 `popup.js` 执行后未观察到长任务，不能排除更早的 Chrome 或操作系统调度等待；`groupingEvaluation` 只给出共享脚本墙钟区间，也不等同于 Long Task 归因。

## 实现范围

正式实现限定于：

- `popup.js`：采集、环形历史、导出和清除逻辑。
- `popup.html`：快速操作底部的性能诊断入口与独立面板。
- `grouping.js`：仅增加弹窗上下文首尾时间点，不改分组逻辑或导出 API。
- `popup.css`：仅当现有 footer 样式无法容纳两个按钮时做最小布局调整。
- `scripts/校验插件.js`：最小自动校验。

`popup.html` 中的诊断入口位于快速操作底部，与“高级管理”同级，不放入高级管理数据面板。优先复用现有样式；若 `.quick-action-footer` 无法容纳两个按钮，才最小修改 `popup.css`。不修改 `background.js` 或 Manifest。

临时的 `baseline-repeat`、`no-auto-duplicate-overview` 和 `startup-resource-prefetch` 实验代码全部删除，不进入正式实现。

## 错误处理

- `performance.now()` 不支持：业务照常，本次不采集也不写历史。
- Paint Observer 不支持：可用绘制边界到达后保存 `measurement: partial`，FCP 字段为 `null`。
- Observer 的 `takeRecords()` 或 `disconnect()` 失败：设置 `freezeStarted` 后捕获异常，标记 `measurement: partial` 并继续生成快照；后续回调不得再修改样本或阻止业务。
- 任一被测调用失败：保持原业务错误传播，同时将对应阶段标为 `error`，不保存错误文本。
- 首次状态读取、状态构建或初次 `render()` 抛错：在现有 `loadState()` catch 中显式设置 `startup: error`；随后恢复控件并让错误界面走同一双帧冻结流程。
- 浏览器宣称支持 Paint Timing 但始终没有 FCP，或首次 `loadState()` 始终不结束：不写历史，避免探针进入尚未确认结束的关键路径。
- session storage 失败：会话字段为 `null`，继续写 local 历史。
- local 历史损坏：只替换性能历史键。
- local 写入失败：不重试，不影响交互；诊断面板显示失败状态。
- Clipboard API 失败：展示只读文本供手工复制。
- 清除失败：保留记录并显示“清除失败”，不得先更新成空状态。

探针代码自身不得抛出未处理异常，不得在 Console 持续输出日志。

## 自动校验

继续扩展现有 `scripts/校验插件.js`，不引入测试框架。至少覆盖：

- `groupingScriptStart`、`groupingScriptEnd` 只在 `document` 和 `performance.now` 可安全使用时记录，后台加载 `grouping.js` 不产生探针全局值；调用抛错时分组逻辑仍正常导出。
- `scriptStart` 位于 `popup.js` 第一条业务逻辑之前；`performance.now` 缺失或抛错时业务继续、时间点为 `null`，临时 grouping 字段仍会删除。非空的三个脚本边界保持单调。
- 每个阶段只记录首次启动调用，包装后成功值和失败语义不变。
- `loadState()` 即使内部捕获异常，也会把首次状态读取、构建或渲染失败记为 `startup: error`；快捷键和重复概览失败不改变 startup。
- Paint Entry 使用 `startTime`；FCP 早于 `render.end` 时 `postRenderFcpDelay` 为 `null`，不能产生负数。Paint Timing 可用时，`navigationToUsable` 必须等于 FCP 和第二帧的较大值；不支持时才退化为第二帧。
- `usableReadyToPaint` 一定晚于初次 `render.end` 和 `controlsReady`；`usablePaintOpportunity` 来自下一次 rAF。
- `window.load` 回调内不会冻结或读取最终 `loadEventEnd`；下一宏任务才设置 `loadEventSettled`，完整样本的 `loadEnd` 必须大于 `0`，否则为 `null` 且 measurement 为 `partial`。
- Paint Timing 支持时，性能历史 storage 读写必须同时晚于 FCP 和 `usablePaintOpportunity`；不支持时必须晚于 `usablePaintOpportunity` 并保存 `partial`。
- 冻结会先设置 `freezeStarted`，合并 `takeRecords()` 返回的最后一批有效条目并断开两个 Observer；排队中的最后一个 Long Task 不会丢失，冻结后的回调和持久化任务不会改变样本。
- 首次 `loadState()` 永久等待或支持 Paint Timing 却始终没有 FCP 时，不启动历史写入。
- 重复概览不会延迟样本冻结，其 `start`、`end` 可分别与 FCP 和可用边界比较。
- 环形历史从 `21` 条裁剪为最新 `20` 条。
- 损坏或未知 schema 只重建性能历史。
- Performance Observer、session storage、local storage 和 Clipboard API 分别失败时，主流程仍成功，并符合 complete、partial 或不写入的约定。
- 导出 JSON 的固定字段齐全，禁止字段和原始错误文本不存在。
- `collecting` 时复制不会读取旧历史，`persisting` 时复制会等待，保存完成后才导出当前样本。
- 清除在当前样本尚未冻结、正在读取历史或已经提交写入三种时序下，最终 local 历史都为空且当前弹窗不会重新追加；session 的已记录样本序号仍可更新。
- 性能诊断按钮和独立面板保持无障碍关联，打开、复制和清除均不调用 `toggleMoreTools()`、`loadManagementState()`、`loadState()` 或 `sendMessage()`。

## 性能验收

探针上线前须证明观察者效应受控：

- 可用绘制边界前不得出现性能历史 storage 读写、数值舍入、JSON 序列化、后台消息或 Console 输出；Paint Timing 支持时，写入还必须晚于 FCP。
- 开发版临时累计每次探针函数自身的同步 CPU 时间，覆盖时间点记录、阶段包装和 Observer 回调，不含被测业务调用。至少 `40` 个热开样本中，中位数不得超过 `1ms`，P95 不得超过 `2ms`；该计数器及其额外计时在交付前删除。
- A/B 使用同一代码版本和同一解压扩展路径，只由一个临时源码常量关闭或开启完整探针。两版共同的测试代码只记录第二个可用 rAF 与 FCP，并用二者较大值生成 `navigationToUsable`，故 A、B 使用完全相同的主指标。交付前删除常量和测试代码，不留下生产开关。
- 热开采用块配对：每次切换后重新加载扩展，丢弃前 `2` 次打开，再采 `10` 次；按 `ABBA BAAB` 执行，共取得 A、B 各 `40` 个样本。将序列按相邻的 `AB` 或 `BA` 分成四对，比较每对块中位数。探针版配对差值中位数不得超过 `max(10ms, 5%)`，任一配对不得超过 `max(20ms, 10%)`。
- 冷开单独采用 `ABBA BAAB ABBA BAAB ABBA`，每个字母都表示切换到对应源码常量后完全退出并重启 Chrome，只采重启后的第一次弹窗，不做预热也不丢弃样本，共取得 A、B 各 `10` 个样本。仍按相邻 `AB` 或 `BA` 配成十对；探针版配对差值中位数不得超过 `max(50ms, 5%)`，超过 `max(100ms, 10%)` 的配对不得多于两对。
- 热开与冷开分别报告 `navigationToUsable` 和 FCP 配对差值，不得以热开通过替代冷开，也不得用 FCP 替代可用指标。
- 复制和清除操作不计入启动指标，但操作失败不得影响其他高级管理功能。

若性能门槛未通过，先缩减采集点或删除探针，不以“监控需要”接受可感知回退。

## 功能验收

- 连续打开弹窗 `21` 次后，只保留最近 `20` 条，顺序和时间正确。
- 同一扩展会话内非空的 `recordedPopupIndex` 单调递增且只有索引 `1` 的样本 `firstRecordedPopup = true`；允许因 local 写入失败出现缺口。
- 重启 Chrome 后会话重新开始；扩展重新加载造成的重置不会被文档称为严格冷开。
- 慢样本可直接看出 `responseEnd`、`responseToGrouping`、`groupingEvaluation`、`groupingToPopup`、Chrome API、状态构建、渲染和 `navigationToUsable` 各段耗时。
- FCP 早于动态渲染时以双帧边界决定可用时间；FCP 晚于双帧边界时以 FCP 决定可用时间，且不会生成负的绘制耗时或早于实际 FCP 的可用指标。
- 业务失败样本在错误界面到达可用绘制边界后仍会保存，并明确标为 `startup: error`；首次加载永久等待或绘制边界始终缺失时明确不计入历史。
- 快速样本即使由 `window.load` 最后满足冻结条件，也会在下一宏任务取得稳定的 `loadEventEnd`；`complete` 样本不会保存 `loadEnd: 0`。
- 冻结前排队的最后一条 Long Task 会被 `takeRecords()` 合并，冻结后 Observer 与性能历史写入不会再改变样本。
- 导出内容不含网址、标题、浏览器对象编号、用户配置和原始错误。
- 当前样本采集中点击复制会得到明确提示，持久化结束后再次复制必然包含当前样本。
- 无论当前样本处于采集还是持久化阶段，清除后历史都保持为空；设置、工作集、最近访问和 session 已记录样本序号均不受影响。
- 打开性能诊断不会触发高级管理数据加载、标签查询或后台消息。
- Manifest 权限、后台启动路径和现有弹窗业务行为不变。

## 自检

- 本设计基于已取得的慢、快样本，不再以 `allTabs` 或重复概览的单次相关性冒充根因。
- FCP 只描述文档第一次内容绘制，不再冒充真实数据可用；主指标是 `navigationToUsable`。
- `navigationToUsable` 取双帧边界与 FCP 的较晚者，故示例慢样本不会把 `5569.7ms` 误报成早于 `6280ms` FCP 的可用时间。
- 写盘严格位于可用双帧边界之后；Paint Timing 支持时还须位于 FCP 之后，故不会抢在被测绘制前读写历史。
- Observer 在不可变快照生成前已排空并断开，`loadEventEnd` 也只在 load 后宏任务读取，故历史写入不会污染本次观测。
- 已知最大的 `responseEnd → popup.js` 区间由 grouping 首尾时间点继续拆分，不会下一次仍只得到同一个黑盒区间。
- 最近 `20` 条足以保留一次异常及其前后样本，无需服务端、数据库或配置系统。
- 会话字段只表达“首个达到冻结边界的可记录弹窗”，没有把提前关闭、扩展重载或序号缺口误判成可证明的实际首开或 Chrome 冷开。
- 点击至 Navigation Timing `0` 的盲区已明确，不能用文档内快样本否定端到端慢体验。
- 文档没有继续保留已被实测否定的性能优化交付承诺。
